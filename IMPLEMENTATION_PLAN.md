## 0. Current state

The repo contains documentation only — the four files in `FanLens_AI_PRD_TRD_Bundle/`. There is no backend, no Android project, no CI. This plan takes the project from empty repo to the TRD §12 Definition of Done.

### Decisions made now (change later if a better reason appears)

| # | Decision | Choice | Why |
|---|---|---|---|
| D1 | Repo layout | `backend/` and `android/` at repo root | Two runtimes, two toolchains; keep them apart |
| D2 | Backend tooling | Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2.0, Alembic, pytest | Matches TRD §2 |
| D3 | Android baseline | Kotlin, Compose, MVVM, DataStore, Room, Glance widget, manual DI (service locator) | TRD §2 allows Glance; manual DI keeps the 5-day build feasible — migrate to Hilt after MVP |
| D4 | LLM | Server-side Gemini, key in server env only | TRD §2 and PRD hard rule |
| D5 | Live updates | Polling first, SSE after Day 3 | TRD §2 allows either for the prototype |
| D6 | Backend auth | Device-token signup (`POST /v1/auth/device`) until the user picks a real scheme | TRD §7 has no auth endpoint; simplest thing that supports private leagues — see Open Questions |

## 1. Backend phases

### B1 — App skeleton and config
- FastAPI app factory, settings via `pydantic-settings`, CORS, request logging (no secrets, no prompts), structured error handler.
- `GET /healthz` returning 200 with version.
- **Files:** `backend/app/main.py`, `backend/app/core/config.py`, `backend/app/core/logging.py`
- **Acceptance:** `uvicorn` boots; `GET /healthz` returns 200; no secrets appear in logs.

### B2 — Database schema and migrations
- Alembic setup; migration creating every TRD §6 table.
- Constraints in the migration, not just the ORM:
  - `(league_id, user_id)` unique on `league_members`.
  - `provider_event_id` unique on `match_events`.
  - `points_ledger` unique on `(event_id, fantasy_team_id, player_id, ruleset_version)` — this is the idempotency key.
  - `points_ledger.ruleset_version` written explicitly, copied from `fantasy_teams.ruleset_id`.
  - `match_events.status` + `source_freshness` columns (`live|delayed|stale|demo`).
  - Corrections table or `superseded_by` column on `match_events` for the audit trail.
- **Files:** `backend/alembic/`, `backend/app/models/*.py`
- **Acceptance:** `alembic upgrade head` runs on an empty Postgres; a test proves the idempotency key rejects a duplicate insert (TRD DoD item 1).

### B3 — League and roster service
- League create/join; invite codes stored **hashed** with expiry (TRD §9); membership check enforced in one shared dependency used by every private endpoint.
- Roster create/update: player count per ruleset, role caps, no duplicate players, exactly one captain and one vice-captain. Store `ruleset_id` on the fantasy team.
- **Files:** `backend/app/services/league_service.py`, `backend/app/services/roster_service.py`
- **Acceptance:** users without membership get 403 on every private read (FR-01); expired invite codes fail; roster violations return 422 with field errors (FR-02).

### B4 — Event adapter and scoring engine (the core of the product)
- **Event adapter:** accepts provider or demo events, validates the payload schema, assigns/keeps stable ID + match + sequence + source timestamp, deduplicates on `provider_event_id`.
- **Scoring engine:** pure function `apply(rule_points, stats, ruleset) -> deltas`. Default ruleset v1 (numbers are a decision — see Open Questions):
  run +1, boundary +1 extra, six +2 extra, wicket (bowled/caught/run-out) +25, catch +8, stumping +12, duck −5, milestones (50→+8, 100→+16, 5-wicket haul→+16), strike-rate bonus for batters, economy bonus for bowlers; captain ×2, vice ×1.5.
- Idempotent ledger write: all deltas in one transaction, keyed by the B2 constraint; replayed event = zero new rows, no total change.
- **Files:** `backend/app/services/event_adapter.py`, `backend/app/services/scoring_engine.py`, `backend/app/data/default_ruleset.json`
- **Acceptance:** unit test per rule; duplicate / out-of-order / corrected event tests all keep totals identical (FR-03); replaying the whole event log reproduces the same totals (TRD DoD item 1).

### B5 — Standings service
- Totals, ranks with deterministic tie-breakers, gap-to-rank-ahead, delta vs previous snapshot, snapshot row written after each scoring transaction.
- Freshness computed from match source timestamps: `live` (<30s), `delayed` (<5min), `stale`, `demo`.
- **Files:** `backend/app/services/standings_service.py`
- **Acceptance:** tie-breakers are deterministic and tested; gap/delta values match hand-computed fixtures (FR-04, FR-09 backend side).

### B6 — HTTP API (TRD §7 surface)
Implement every endpoint from the sketch: the nine listed plus `POST /v1/auth/device` and `POST /v1/matches/{id}/events` (provider-normalized ingest behind `/demo` for the prototype).
- Membership dependency on every private route; rate limits on join, invite-generate, and AI endpoints (TRD §9).
- Cursor pagination `?after=` on the events feed.
- **Acceptance:** API tests cover unauthorized reads, invite expiry, rate limiting, pagination boundaries (FR-01, FR-11).

### B7 — Insight service (Rivalry Intelligence)
- Trigger detection: rank swap, gap-threshold crossing, followed-player impact, match end, direct user question (TRD §8).
- Prompt builder sends **only** server-computed facts: event IDs, deltas, ranks, ruleset version, display names, tone preference.
- Validator: JSON schema OK → every number matches server facts → every event ID exists in the match. Any failure → deterministic template (e.g. "You gained 34 pts: Rahul 55 runs + 1 catch; now 2nd, 18 pts behind Priya."). Template fallback also covers timeout/quota.
- Insights cached and deduped per (league, league_user, trigger, window) with per-user rate limits.
- **Files:** `backend/app/services/insight_service.py`, `backend/app/ai/gemini_client.py`, `backend/app/ai/prompt_builder.py`, `backend/app/ai/validator.py`, `backend/app/ai/templates.py`
- **Acceptance:** tests for malformed JSON, invented number, invented event ID, prompt injection in a display name, quota failure — every one ends in a template, never in a wrong number (FR-08, TRD DoD item 6).

### B8 — Demo event feed
- `POST /v1/demo/matches/{id}/events` injects scripted events (ball-by-ball timeline fixture); marks the match `demo` freshness; only enabled with demo credentials/env flag (TRD §2 separate demo credentials).
- **Acceptance:** a full demo script drives points → standings → insight without any provider (FR-12).

### B9 — Security, privacy, deployment
- Hashed expiring invite codes (done in B3), HTTPS-only, env-var secrets with least privilege, `.env.example` with no real values, rate limiting, retention/deletion job stub for user and event data.
- Managed Postgres + managed API host; separate demo and prod environments with separate credentials.
- **Acceptance:** a checklist run — no key material in the Android app or the repo, invite hashes unreadable, TLS enforced (FR-11, PRD §9 non-goals).

## 2. Android phases

### A1 — Project skeleton
- Gradle + Kotlin + Compose, minSdk 26, target latest stable; modules for `data`, `ui`, `overlay`, `widget`; manual DI service locator.
- Logging, ProGuard rules, debug/release build types.
- **Acceptance:** empty app builds and installs.

### A2 — Data layer
- API client (OkHttp + kotlinx.serialization) with freshness fields on every payload; device-token auth header.
- Repositories: league, roster, event feed, standings, insights, preferences.
- Room cache for standings/events; DataStore for preferences (companion_mode, overlay_enabled, refresh policy, triggers, gap threshold, quiet hours, motion level, widget fields, notification categories, ai_enabled, tone).
- Preferences serialize to the exact PRD §6 names; `PATCH /v1/me/preferences` sync for AI-tone server-side.
- **Acceptance:** repository tests against a fake API; preference round-trip test; a unit test proves `TAP_TO_ACTIVATE` never writes a "proactive allowed" flag (FR-07, FR-11).

### A3 — Core UI
- League list / create / join screens; roster editor (roles, captain/ vice picker, validation messages); standings screen with rank, totals, gaps, deltas and freshness chip; event history / recap (P1, FR-10); mascot panel opening on tap.
- **Acceptance:** every screen renders against the demo feed; freshness chip is always visible with a timestamp (FR-04, FR-09, FR-01, FR-02, FR-10).

### A4 — Overlay service and widget
- `CompanionOverlayService`: `WindowManager` + `TYPE_APPLICATION_OVERLAY`, permission check with rationale, settings deep link on denial/revocation, draggable ball, hide/dismiss, tap → panel/refresh/explain.
- Proactive behavior gated by: companion_mode, overlay_enabled, trigger categories, gap threshold, quiet hours, cooldowns; reduced-motion honored.
- Widget: Glance, fields per `widget_fields` pref, freshness status, deep link; renders from cache — works when the overlay permission is denied (TRD DoD item 4).
- **Acceptance:** mode persists across restart (DoD item 2); TAP_TO_ACTIVATE produces zero unsolicited animation/AI (DoD item 3); permission denied/revoked → app + widget still useful (DoD item 4); dismiss/hide works (FR-05, FR-06, FR-07).

### A5 — Refresh policy and offline states
- `AUTO` / `ON_OPEN` / `MANUAL` honored exactly; polling loop or SSE when available; offline/demo/stale banners with per-policy behavior.
- **Acceptance:** manual mode never polls; on-open fetches once per open; failures show a deterministic fallback, never a frozen UI (FR-09, FR-12).

## 4. Test plan (TRD §10, verbatim coverage)
- **Unit:** scoring rules, captain multipliers, roster constraints, tie-breakers, triggers → pytest suite in `backend/tests/unit/`.
- **Integrity:** duplicate, out-of-order, corrected events; full replay equality.
- **API:** membership, invite expiry, unauthorized reads, rate limiting, fallback responses.
- **Android (JUnit + Robolectric + instrumentation where needed):** mode persistence, permission denied/revoked, lifecycle, dismiss/hide, reduced motion, stale-data states.
- **AI:** malformed JSON, invented number, invented event ID, prompt injection, quota/timeout, template fallback.
- **Demo:** scripted match — event → points → standings → Always Reactive insight; switch to Tap to Activate and verify no proactive insight.

## 6. Definition of done — sign-off checklist (TRD §12)
- [ ] Replaying a simulated event does not double-count points.
- [ ] Mode switch persists across app restart.
- [ ] Always Reactive surfaces configured insights where permitted; Tap to Activate suppresses all proactive mascot and AI behavior.
- [ ] Widget/app stay useful when overlay permission is denied.
- [ ] Freshness visible; offline / AI / provider failure has a fallback.
- [ ] AI numeric claims match server facts, or a template is used.
- [ ] No unsupported external fantasy-platform integration is claimed.

Run before claiming any task done:

cd android; .\gradlew.bat testDebugUnitTest

## 7. Open questions to resolve before Phase 1 (blockers first)
1. **Default ruleset numbers** (§B4 table above are a proposal — cricket point values must be confirmed).
2. **Auth scheme** — device token (simple) vs email OTP vs Google sign-in. Affects B6, A2.
3. **Demo storage** — same Postgres as prod with a demo flag, or a separate demo DB? Affects B9.
4. **Hosting** — Render/Fly/Railway for the API, Supabase for Postgres, or something else? Affects B9 and Day 5.
5. **LLM key** — which Gemini key/account, and per-user quota expectations for the demo.

## 8. Known risks and mitigations (PRD §11)
- **No authorized roster/score API from fantasy platforms** → FanLens-managed rosters plus permitted imports only; never scrape (B3, B9).
- **Data latency** → freshness always visible; demo mode as first-class state (B5, B8, A5).
- **Android background/overlay limits** → overlay optional, dismissable, with widget and in-app fallbacks; never sell instant reaction (A4).
- **AI hallucination** → compute server-side, validate or template every insight (B7).
